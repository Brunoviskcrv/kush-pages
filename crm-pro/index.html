Fluxos

Como funciona

→
Autenticação Telegram OTP
1
Vendedor digita @username na tela de login
2
Backend gera OTP 6 dígitos e envia via Telegram bot
3
Usuário cola o código na interface web
4
Backend valida OTP, gera JWT com role + lojas + permissões
5
Frontend salva JWT no localStorage e redireciona ao dashboard
→
Visualização com RBAC
1
Request chega com Authorization: Bearer <JWT>
2
Middleware valida JWT e checa session_version no cache (TTL 60s)
3
Role e permissões granulares extraídas do payload
4
Filtro de loja aplicado automaticamente para vendedores
5
Dados financeiros retornados apenas para role gestao
→
Registro de Tratativa
1
Vendedor abre perfil do cliente e registra tratativa
2
Backend faz INSERT em crm_tratativas
3
UPSERT sincroniza entrada na crm_overrides.timeline do cliente
4
Feed de Atividade do Dashboard é atualizado em tempo real
5
Timeline Geral e Histórico CRM do perfil refletem a tratativa
Módulos

Componentes principais

Auth Telegram
Login sem senha via OTP enviado ao Telegram do usuário, com JWT de sessão diária e revogação de emergência em menos de 60 segundos.
OTP de 6 dígitos com validade de 5 minutos
JWT com expiração às 19h BRT (segurança operacional diária)
session_version: incremento revoga todos os tokens ativos do usuário
Rate limit: 3 tentativas/min por @username + 10/min por IP
Fallback API Key para integrações server-to-server
POST /auth/telegram/verify { code: "847291" }
{ token: "eyJ...", user: { nome: "Bruno", role: "gestao", lojas: [...] } }
RBAC & Permissões
Controle de acesso em duas camadas: role base (gestao/admin/vendedor) e 5 permissões granulares configuráveis individualmente pelo admin.
3 roles com escopos crescentes de visibilidade
Filtro automático de loja para vendedores (sem config manual)
Dados financeiros (receita, ticket, top clientes com gasto) exclusivos para gestao
Export CSV restrito a admin e gestao
Cache de sessão 60s — performance sem abrir mão de segurança
GET /api/stats/top-clientes (role: vendedor)
{ clientes: [...] } // colunas gasto_total e ticket_medio omitidas
Dashboard & Analytics
Visão operacional em tempo real com 7 segmentos de clientes, análise de inatividade por faixa e dashboard comparativo de receita mensal por loja.
7 segmentos: VIP, Em Risco, Perdido, Regular, Fiel, Novo, Lead
Inatividade em 4 faixas: 0-30, 31-60, 61-90, 90+ dias
Comparativo de 3 meses: receita, pedidos, ticket médio, clientes ativos
Breakdown por loja lado a lado (6 lojas)
Feed de atividade recente com tratativas em tempo real
GET /api/stats/inatividade?loja=Elite+Vape+420
{ d0_30: 6124, d31_60: 4751, d61_90: 3990, d90p: 36955 }
Gestão de Contatos
Lista completa dos 51.820 clientes com busca, filtros avançados, presets salvos, paginação com 1.037 páginas e ação em massa no termômetro.
Filtros por fase, termômetro, loja e inatividade
Presets salvos (ex: 'VIPs sem comprar 60 dias')
Paginação avançada: primeiro/último/ir para página X
Ação em massa: classificar até 500 clientes de uma vez
Perfil completo com timeline de tratativas e histórico CRM
PUT /api/clients/bulk-termometro { ids: [88,99,102], termometro: "Quente" }
{ updated: 3, errors: 0 }
Timeline & Calendário
Registro cronológico de todas as tratativas da operação e calendário de follow-ups agendados, vencidos e do dia.
Feed cronológico: quem falou com quem, quando e resultado
Tratativa registrada sincroniza em 3 lugares: perfil, dashboard e timeline
Calendário com follow-ups do dia, vencidos e futuros
Histórico formatado (old→new, tags, notas, datas legíveis)
Visibilidade por loja conforme role do usuário
POST /api/tratativas { cliente_id: 4821, nota: "Interessado em recompra", follow_up: "2026-05-28" }
{ id: 9043, timeline_updated: true, dashboard_feed: true }

Filosofia

O que guia cada decisão

⭐
"Dar ao vendedor a informação certa, na hora certa, sem nenhuma fricção de acesso — e à gestão a visibilidade financeira que nenhuma planilha consegue entregar."
PRINCÍPIO 01
Integrações adicionam, nunca substituem — nenhuma funcionalidade estável é removida por uma integração nova
PRINCÍPIO 02
Segurança por camadas — JWT + OTP + session_version + rate limit: cada camada falha com segurança independente das outras
PRINCÍPIO 03
Zero configuração para o usuário final — filtros de loja, permissões e expiração de sessão acontecem automaticamente, invisíveis a quem opera
Filtro de feature
Se uma mudança pode regredir autenticação, permissões ou integridade de dados da base de 51.820 clientes, ela precisa de alinhamento explícito, documentação no ARCHITECTURE.md e validação manual em produção antes do merge.
